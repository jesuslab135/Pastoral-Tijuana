## Task 11 CI failure — diagnosed and fixed (2026-08-11)

The red run was https://github.com/jesuslab135/Pastoral-Tijuana/actions/runs/31492403292: Vet ✓, Lint ✓, Test ✗.

**Root cause: the advisory lock was silently released, so it never serialized anything.** `testdb.acquireProcessLock` held its dedicated connection in a local variable that nothing kept reachable after the function returned. A session-level advisory lock lives and dies with its connection, and Go's `net` socket finalizer closes an unreachable connection on the next GC — so the first GC cycle handed the lock back to Postgres. Two test binaries then migrated a brand-new database at the same time and collided on `CREATE EXTENSION citext` (duplicate key on `pg_extension_name_index`) and on the seasons seed (`liturgical_seasons_date_range_excl`). Local runs never showed it because the local `pastoral_test` database was already migrated, which makes the concurrent migration a no-op.

Proof, before the fix: a probe that acquired the lock exactly the way `testdb` did, then called `pg_try_advisory_lock` from a second session, reported the lock held immediately after acquisition and **released after three GC cycles**.

Fix (`e339592`): store the connection in a package-level `lockConn` so it stays reachable for the process lifetime, and fail loudly if it was not retained. No CI step was weakened — no `continue-on-error`, no `-p 1`, lint and test both still run at default parallelism.

The container-based reproduction is worth keeping; it is the only way to see a first-time-migration bug from this laptop, since CI gets an empty Postgres and Linux while the local database is long-since migrated:

```bash
docker network create ci-repro-net
docker run -d --name ci-repro-pg --network ci-repro-net \
  -e POSTGRES_USER=pastoral -e POSTGRES_PASSWORD=pastoral -e POSTGRES_DB=pastoral_test postgres:16
until docker exec ci-repro-pg pg_isready -U pastoral; do sleep 2; done
docker run --rm --network ci-repro-net -v "<repo-path>:/src" -w /src/backend \
  -e TEST_DATABASE_URL="postgres://pastoral:pastoral@ci-repro-pg:5432/pastoral_test?sslmode=disable" \
  golang:1.23 sh -c "go vet ./... && go test ./... -count=1 -v" 2>&1 | tail -80
# lint exactly as CI does:
docker run --rm -v "<repo-path>:/src" -w /src/backend golangci/golangci-lint:v1.62.2 golangci-lint run ./...
# cleanup (only these): docker rm -f ci-repro-pg ; docker network rm ci-repro-net
```

### Decisions made during execution (these override earlier plan text)

1. **`middleware.RealIP` removed** (user ruling, 2026-08-11). chi deprecated it over IP-spoofing advisories: it trusts `X-Forwarded-For` unconditionally and Caddy *appends* to that header, so a client can prepend a forged address. Task 7's plan text originally mandated it; the plan file has been corrected. **Plan 2 must resolve the client IP from a header Caddy sets itself, trusted only from Caddy's address, before the login rate limiter is built** — otherwise per-IP throttling is bypassable.
2. **Test database access is serialized by a Postgres advisory lock** (`testdb.New` takes `pg_advisory_lock(987654321)` once per test binary on a dedicated connection held for the process lifetime). Without it, `go test ./...` fails: packages run in parallel against one shared database and corrupt each other's fixtures. Any new package whose tests touch Postgres must go through `testdb.New` so it inherits this. **The lock connection must stay reachable in a package-level variable** — an unreferenced connection is closed by the GC's socket finalizer, which releases the lock without any error; see the Task 11 diagnosis above.
3. **Dependencies are pinned to hold the `go 1.23.x` directive**: goose v3.26.0, pgx v5.7.6, chi v5.3.1, google/uuid v1.6.0. Newer releases demand a higher Go directive. When adding a dependency, check `head -5 backend/go.mod` afterwards and downgrade the dependency rather than accepting a directive bump.
4. **Never commit build artifacts.** `go run`/`go build` on Windows can drop `backend/api.exe`; Task 1 committed one and needed a history rewrite to remove it.

**Spec refinement recorded during planning:** cancellation with notify requires the event to remain in the .ics feed with `STATUS:CANCELLED`, so `events` gains a `cancelled_at timestamptz NULL` column (soft cancel). `DELETE ?notify=true` sets `cancelled_at`; `?notify=false` hard-deletes. Public JSON excludes cancelled events; .ics includes them (cancelled within the last 90 days) so subscribed phones remove them.
